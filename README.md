# roost

[English version](README.en.md)

Место, где консольный ИИ-агент работает под присмотром. Машина, которая у вас
есть, — одноплатник, мини-ПК, старый ноутбук, VPS — получает группу с
предсказуемым выходом в интернет, обёртку запуска агента, tmux-сессии по
проектам и одинаковую с остальными машинами раскладку репозиториев и
окружения.

> **Статус: в разработке.** Изоляция трафика, сессии, синхронизация
> окружения, раскладка проектов, обёртка `roost` и снос — написаны и
> проверены на живом железе (Raspberry Pi): установка идемпотентна на втором
> прогоне, группа и правила появляются, снос не оставляет ни файлов, ни
> правил ни в одной адресной семье.

**Чего roost не делает: не пускает вас к этой машине снаружи.** Ни
веб-терминала, ни тоннеля, ни публичного входа — это отдельная задача с
отдельными владельцами. Сессии здесь — обычный tmux, поэтому подойдёт любой
инструмент, который умеет tmux: [pockterm](https://github.com/hitromudr/pockterm)
как веб-терминал, `ssh -t`, `mosh`, что угодно ещё. Так сделано после того,
как roost и уже стоявший на машине веб-терминал схлестнулись за один и тот же
systemd-юнит; подробности — в разделе «Границы».

## Быстрый старт

```bash
git clone https://github.com/<owner>/roost && cd roost
./roost setup      # несколько вопросов, ответы уходят в roost.conf
./roost install    # применить к этой машине
./roost doctor     # проверить, что песочница — то, чем себя называет
```

Профили `pinned` и `proxied` требуют `PROXY_URL` в
`/etc/roost/agent-proxy.env` (0640, владелец — учётная запись агента). Без
него агент остаётся **без сети вообще**, и `doctor` говорит об этом прямо.

## Что делают роли

| Роль | Что |
|---|---|
| `egress_sandbox` | группа и правила `gid-owner`, обёртка запуска агента |
| `agent_sessions` | tmux-сессии по проектам, mouse mode для телефона |
| `projects` | клоны репозиториев из `projects.conf` |
| `env_sync` | репозиторий окружения и его установщик |

Ролям нужен только `ansible.builtin` — никаких коллекций ставить не надо.

### Проекты: список, а не раздача

`projects.conf` перечисляет репозитории, которые должны быть на **каждой**
машине, откуда вы работаете:

```
isearch  https://git.example/isearch.git
sorter   https://github.com/x/sorter.git  develop
```

`./roost projects` приводит ту машину, где запущен, к этому списку. Общее
состояние держит репозиторий, а не одна из машин, поэтому команда одинаково
уместна и там, где живут агенты, и на рабочем ноутбуке.

Ничего существующего при этом не переписывается. Клон с незакоммиченной
работой называется и пропускается; имя, занятое каталогом без `.git`
(развёрнутый артефакт, цель деплоя), — тоже, и остальной список всё равно
раскладывается. Ветку можно не указывать — тогда берётся ветка репозитория
по умолчанию.

Окружение (`env_sync`) устроено так же: репозиторий с конфигами
выкладывается и запускается его собственный установщик. Если в нём есть
зашифрованные файлы (`*.sops.*`), роль требует age-ключ на месте — без него
секреты молча останутся зашифрованными, а установщик отчитается об успехе.

Плейбуки запускаются из корня репозитория — там `ansible.cfg`, который
указывает на `ansible/roles`.

## Зачем

Разработка с агентом привязывает вас к машине, на которой он запущен.
Ноутбук закрыт — работа стоит. Перенести агента на постоянно включённый
сервер несложно, но всплывают две вещи, которые приходится решать каждому
заново:

- **Выход в интернет.** Агенту нужен доступ к своему API. Если сервер меняет
  сеть или стоит за NAT, внешний адрес плавает. roost запирает трафик агента
  в группе, которой разрешён только локальный прокси, — выход становится
  предсказуемым и не зависит от того, где сейчас находится машина.
- **Окружение.** Агент полезен настолько, насколько ему знакома ваша среда:
  конфиги, ключи, контекст проектов. roost раскладывает их одинаково на всех
  машинах, а секреты держит зашифрованными.

Третья вещь — доступ снаружи — намеренно оставлена другим инструментам.

## Границы

Машина, где стоит агент, обычно не пустая: на ней уже есть веб-терминал,
тоннели, чужие юниты и своя история. Правило здесь одно: **roost владеет
только тем, что сам поставил.**

Это не осторожность ради красоты. Ранняя версия ставила веб-терминал сама и
на машине, где он уже был, сгенерировала ему второй токен — тот, о котором не
знал ни обратный прокси, ни ссылка из меню. Каждый запрос стал отвечать
`401`, а браузер показывал это как машину без сессий; на диагностику ушёл
вечер. Двое владельцев одного юнита ломают его при первом же расхождении, и
единственная надёжная защита — не становиться вторым.

Поэтому `roost uninstall` снимает правила, обёртку, помощник сессий и
`/etc/roost` — и не трогает ничего другого, даже если оно выглядит частью
той же картины.

## Модель безопасности

Изоляция агента здесь — про предсказуемость исходящего трафика, а не про
защиту от вредоносного кода: агент работает от вашего пользователя и делает
с вашими файлами то же, что и вы.

Если вы отдаёте сессии наружу чем-то ещё, помните: **терминал отдаёт полную
оболочку тому, кто до него дошёл.** Относитесь к такому доступу как к SSH.

## Разработка

```bash
make help     # список целей
make check    # линт и тесты
```

Роли `projects` и `env_sync` покрыты тестами, которые прогоняют их
по-настоящему во временных каталогах — нужен только ansible, ни docker, ни
root. Там, где ansible нет, эти тесты пропускаются.

## Как снести

```bash
./roost uninstall --dry-run   # показать, что уйдёт и что останется
./roost uninstall             # спросит подтверждение
./roost uninstall --purge     # плюс группа песочницы и roost.conf
```

Уходят: правила и их юнит, обёртка запуска, помощник сессий, каталог
`/etc/roost`. Остаются ваши проекты и запущенные сессии — их снос требует
явного решения, а не флага по умолчанию, — и всё, что roost не ставил.

Проверено в контейнере: после сноса не остаётся ни одного правила ни в
IPv4, ни в IPv6, и машина возвращается в исходное состояние.
