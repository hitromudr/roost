# roost

[English version](README.en.md)

Установщик для машины, на которой работают консольные ИИ-агенты. Та, что у вас
есть — одноплатник, мини-ПК, старый ноутбук, VPS — получает песочницу с
предсказуемым выходом в интернет, сам агент, tmux-сессии по проектам, вашу
раскладку репозиториев и веб-терминал, чтобы дойти до всего этого с телефона.

## Как это работает

Одна цепочка, и всё остальное в этом файле — её части:

```
телефон → фронт (TLS) → терминал на loopback → сессия tmux → agent-run → агент
```

- **Агент** живёт в группе `agent-sandbox`. Правила `gid-owner` разрешают ей
  только loopback, то есть локальный прокси, — а он снаружи песочницы. Выход
  становится предсказуемым и не зависит от того, где сейчас машина.
- **Сессия** — обычный tmux, запускающий агента через обёртку `agent-run`.
  Обычный настолько, что подойдёт `ssh -t` или `mosh`, а не только терминал ниже.
- **Терминал** — [pockterm](https://github.com/hitromudr/pockterm): отдельный
  проект, один Go-бинарь с мобильной PWA внутри. Показывает tmux-сессии и
  подключается к выбранной; **сам сессий не создаёт** — их создаёт Makefile,
  который roost направляет на `agent-run`. Слушает только loopback.
- **Фронт** — TLS и замок перед терминалом: nginx на этой же машине, если у неё
  есть адрес, или гейт, если его нет.

Три слова, которые дальше используются как термины:

| Слово | Значит |
|---|---|
| **стенд** | машина, где живут агенты: песочница, сессии, терминал |
| **гейт** | машина с публичным адресом, через которую видно стенд за NAT |
| **сессия** | tmux-сессия по проекту, `roost-<проект>`, с агентом внутри |

## Что нужно от машины

- Linux с systemd и `sudo`; пакетный менеджер `apt`, `dnf`, `pacman`, `zypper`
  или `apk` — ansible roost поставит сам.
- Свободный порт для TLS (`8443` по умолчанию) — если терминал отдаётся с этой
  же машины; когда её отдаёт гейт, порт нужен на нём. И, если терминал ставится,
  ~200 МБ на его сборку: тулчейн Go скачивается в `/opt/roost` и уходит при сносе.
- Домен **не обязателен**: имя выводится из адреса машины через `sslip.io`.
- Публичный адрес не обязателен: машине за NAT нужен гейт — вторая машина с
  адресом и sshd.

## Быстрый старт

```bash
git clone https://github.com/hitromudr/roost && cd roost
./roost up
```

Одна команда делает по порядку:

1. задаёт несколько вопросов и пишет ответы в `roost.conf`;
2. ставит ansible, если его нет;
3. ставит агента, если его нет;
4. заводит группу-песочницу и правила выхода;
5. поднимает терминал на loopback и направляет его кнопки на `agent-run`;
6. открывает к нему доступ: сертификат и свой vhost — или туннель к гейту;
7. прогоняет `roost doctor` и печатает QR-код для телефона.

При `client_auth=mtls` последним печатается не код терминала, а приглашение для
устройства (`roost enroll phone`): телефон без сертификата за эту дверь всё
равно не пустят.

На телефоне: сканировать код, затем «добавить на главный экран» — страница
ведёт себя как приложение, в своём окне и без вкладок. Войти в аккаунт агента
можно уже оттуда: сессия открывает обычный экран входа.

Каждый шаг доступен отдельной командой, потому что каждый касается того, у чего
на машине может быть свой владелец. `roost install` при этом означает ровно то,
что означал всегда — песочница, сессии, окружение — и терминала не ставит.

## Доступ с телефона

Терминал всегда слушает loopback. Наружу его отдаёт одно из двух.

### У машины есть свой адрес

```bash
./roost expose      # свой файл vhost в nginx, сертификат Let's Encrypt
./roost qr          # код с адресом и токеном
```

Домена может не быть: тогда имя выводится из адреса машины через `sslip.io`
(`203-0-113-5.sslip.io`), и сертификат всё равно настоящий — значит, страницу
можно поставить как приложение.

### Машина за NAT: гейт

Нужна вторая машина с маршрутизируемым адресом. `gate=` в конфиге говорит,
какая:

```bash
# gate=roost-tunnel@vps.example
./roost tunnel        # на стенде: свой ключ и юнит с одним обратным форвардом
./roost gate          # печатает то, что нужно добавить на гейте
./roost gate --apply  # или ставит это по вашему ssh-доступу
```

Гейт получает три вещи, каждая названа по roost — чтобы владелец мог убрать их
по имени:

| Что | Зачем |
|---|---|
| строка в `authorized_keys` | `restrict,port-forwarding,permitlisten="127.0.0.1:18130"` — один форвард, и больше ничего: ни оболочки, ни агента, ни второго порта |
| `/etc/ssh/sshd_config.d/roost-tunnel.conf` | без него укреплённый sshd форвард не разрешит |
| `/etc/nginx/conf.d/roost-terminal.conf` | отдаёт терминал через форвард |

Сертификат выпускается **на гейте**: адрес у него, значит и имя доказывает он.
Аккаунт для туннеля создаёт владелец гейта сам — `--apply` этого не делает.

При `client_auth=mtls` фронт — тоже гейт, поэтому клиентские сертификаты
проверяет его nginx: туда нужно скопировать `ca.crt` и `ca.crl` (команду печатает
`roost gate`). Список отзыва при этом приходится довозить заново после каждого
`roost-ca revoke`: список, которого фронт не видел, ничего не закрывает.

Кнопки в ящике сессий — те, что создают сессию с телефона, — запускают агента
**через `agent-run`**, то есть в песочнице. `roost doctor` проверяет именно это:
кнопки, которые работают, но ничего не изолируют, выглядят как успех. Как этот
стык устроен — в [«Почему так»](#почему-так).

**Гейт на пути агента — не файл roost, но его отсутствие roost показывает.**
Стенд бывает полон и всё равно оставляет открытым самый короткий путь: имя
агента в PATH. Так было на запасном ноутбуке 2026-08-21 — `doctor` зелёный по
всем проверкам, а `claude` в PATH оказался симлинком прямо на бинарь, поэтому
вызов по имени (оболочка, скрипт, юнит, cron, ssh) шёл мимо песочницы и с
прямого адреса машины. Ставит гейт хозяйский `install-agent-gates.sh` из
`dotfiles` — он нужен и на машинах, которыми roost не управляет, а второй
установщик на один путь и есть та ссора владельцев, которой правило «владеет
только тем, что сам поставил» избегает. Роль roost здесь — **замер**: `doctor`
зовёт путь агента под логин-группой учётной записи и ждёт отказа. Файл
root:root с битом исполнения о том, что он делает при запуске, не говорит
ничего.

## Замок: токен или сертификат

| | `token` (по умолчанию) | `mtls` |
|---|---|---|
| что закрывает дверь | строка в ссылке, которую сохранил телефон | клиентский сертификат на устройстве |
| сколько шагов | один: сканировать QR | два: поставить сертификат, затем открыть терминал |
| где живёт секрет | в истории браузера и в логах фронта | в хранилище телефона, наружу не читается |
| сменить | `roost token` — и все телефоны сканируют новый код | `roost enroll <устройство>` для каждого, по одному |
| потеря телефона | сменить токен: остальные устройства тоже переподключатся | `roost-ca revoke <устройство>` — остальные не затронуты |

Выдать устройству сертификат:

```bash
./roost enroll phone
```

Печатается QR с **одноразовой ссылкой** на пакет устройства и пароль, который
спросит импортёр. Ссылка живёт десять минут — использовали её или нет.

Убрать потерянное устройство:

```bash
sudo roost-ca revoke phone && sudo systemctl reload nginx
```

Это команды для фронта — той машины, где стоит nginx с сертификатами. Когда
фронт на гейте, туда же после отзыва едет обновлённый `ca.crl`.

## Команды

| Команда | Что делает |
|---|---|
| `roost up` | всё по порядку: агент, песочница, терминал, вход, QR |
| `roost setup` | вопросы; ответы уходят в `roost.conf` |
| `roost install` | песочница, сессии, окружение |
| `roost agent` | ставит агента, если его нет; записывает найденный путь в конфиг |
| `roost terminal` | терминал — только там, где своего нет |
| `roost expose` | TLS впереди терминала на этой же машине |
| `roost tunnel` | обратный туннель к гейту, для машины без своего адреса |
| `roost gate [--apply]` | печатает (или ставит) то, что нужно на гейте |
| `roost enroll <устройство>` | выдаёт устройству клиентский сертификат |
| `roost qr` | QR-код с адресом и токеном |
| `roost token` | меняет токен терминала и печатает новый код |
| `roost projects [--list]` | приводит машину к списку из `projects.conf` |
| `roost doctor` | проверяет, что стенд — то, чем себя называет |
| `roost uninstall [--purge] [--dry-run]` | снимает то, что roost поставил |

Флаги, меняющие разговорчивость: `--yes` у `up`, `expose`, `gate` и `uninstall`
не задаёт вопросов, `--dry-run` у `uninstall` только показывает, `--print` у
`expose` печатает рецепт вместо установки.

## Настройка

Всё в `roost.conf`; `roost setup` пишет его по ответам, а
[`roost.conf.example`](roost.conf.example) объясняет каждую строку. Файл
гитигнорен: в нём адреса и учётные данные одной машины.

Шесть ключей решают, какой машина получится:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `egress_profile` | `pinned` | `pinned` — только loopback, выход через локальный прокси; `proxied` — плюс адреса из ansible-переменной `egress_sandbox_allow` (в `roost.conf` их не задать); `direct` — без ограничений |
| `proxy_url` | пусто | прокси, через который выходит агент. Пишется в `/etc/roost/agent-proxy.env` (0640) |
| `expected_exit` | пусто | адрес, с которого трафик агента **должен** выходить. `doctor` сверяет |
| `terminal` | `true` | ставить ли терминал |
| `gate` | пусто | `user@host` машины с публичным адресом, если у этой его нет |
| `client_auth` | `token` | замок: `token` или `mtls` |

Остальное — где лежат проекты и репозиторий окружения, адрес терминала, имя и
порт для телефона, почта для Let's Encrypt, пробник выходного адреса, порт
форварда на гейте — умолчаниями годится как есть; каждый ключ объяснён в
`roost.conf.example`, а те, о которых есть разделы ниже, — в них.

> **Проверьте выходной адрес, прежде чем входить агентом в аккаунт.** Прокси,
> который отвечает, — это ещё не прокси, который меняет адрес: локальный
> `3proxy` на том же сервере выпустит трафик с адреса этого же сервера. Запрос с
> неожиданного адреса — повод приостановить учётную запись. `roost doctor`
> печатает найденный адрес и сверяет его с `expected_exit`; пока там пусто, он
> говорит, что сравнивать было не с чем.

Профили `pinned` и `proxied` без `PROXY_URL` оставляют агента **без сети
вообще** — он падает на первом запросе, и `doctor` говорит об этом прямо.

## Проекты и окружение

`projects.conf` перечисляет репозитории, которые должны быть на **каждой**
машине, откуда вы работаете:

```
notes   https://git.example/you/notes.git
webapp  https://github.com/example/webapp.git  develop
```

`./roost projects` приводит ту машину, где запущен, к этому списку — одинаково
уместно и на стенде, и на рабочем ноутбуке. Ничего существующего не
перезаписывается: клон с незакоммиченной работой называется и пропускается, имя,
занятое каталогом без `.git`, — тоже, остальной список раскладывается.

Окружение задаётся `env_repo`: репозиторий выкладывается в
`<project_dir>/dotfiles` и запускается его собственный установщик (`./install.sh`).
Если в нём есть зашифрованные файлы (`*.sops.*`), роль требует age-ключ на
месте — без него секреты молча останутся зашифрованными, а установщик отчитается
об успехе.

## Второй агент

Первый задаётся ключом `agent_command`; пусто означает «поставить Claude Code и
записать сюда выбранный путь». Остальные перечисляются рядом:

```
agents=codex:/home/you/.local/bin/codex
```

`roost install` ставит `/usr/local/bin/codex-safe` — ссылку на тот же
`agent-run` — и `/etc/roost/agents/codex.env`, где назван только бинарь. Группа,
прокси и профиль остаются машинными: политика одна на всех агентов.

## Границы: чем roost владеет

**roost владеет только тем, что сам поставил.** Отсюда четыре правила, которым
следует код:

1. **Терминал ставится только там, где своего нет.** `pockterm.service` без
   `/etc/roost/terminal.env` рядом — признак чужого владельца, и роль
   останавливается. Что делать вместо этого: поставить roost с `terminal=false`
   — песочница, сессии и окружение от терминала не зависят — и направить
   имеющийся терминал на сессии, которые roost создаёт; они обычный tmux.
   Снести чужой юнит roost не предложит.
2. **roost владеет файлами, а не сервисами.** В чужой nginx добавляется один
   файл; `nginx -t` проверяется до перезагрузки, и при отказе файл забирается
   назад. Сама перезагрузка — с явного согласия.
3. **Чего roost не может присвоить, он печатает.** Входная дверь, куда файл не
   положить (Caddy через admin API, чужой гейт), получает печатный рецепт.
4. **Всё добавленное снимается по имени.** Снос читает файлы состояния;
   pockterm сносится его собственным установщиком.

Что именно появляется на машине:

| Часть | Где |
|---|---|
| правила и их юнит | `/usr/local/sbin/egress-firewall`, юнит `egress-firewall` |
| пускатели: `agent-run`, `agent-exec`, `roost-session` | `/usr/local/bin` |
| агент | `~/.local/bin/claude` по умолчанию |
| терминал | юнит `pockterm`, `/etc/pockterm`, исходники и тулчейн в `/opt/roost` |
| фронт | `/etc/nginx/conf.d/roost-terminal.conf` — здесь или на гейте, если он есть |
| удостоверяющий центр (при `mtls`) | `/etc/roost/ca` (0700) |
| туннель (при `gate=`) | юнит `roost-tunnel`, ключ в `/etc/roost/tunnel` |
| что именно roost поставил | `/etc/roost/*.env` |

## Модель безопасности

Песочница здесь — про предсказуемость исходящего трафика, а не про защиту от
вредоносного кода: агент работает от вашего пользователя и делает с вашими
файлами то же, что и вы.

**Терминал отдаёт полную оболочку тому, кто до него дошёл.** Относитесь к такому
адресу как к SSH. По умолчанию дверь закрыта токеном за TLS — этого хватает,
чтобы начать; для постоянной установки ставьте клиентские сертификаты
(`client_auth=mtls`).

Секретов в репозитории нет. Всё машинное — учётные данные прокси, адреса,
список репозиториев — это конфигурация: `roost.conf`, `projects.conf` и
`ansible/inventory` гитигнорены, наружу едут только `.example`.

## Что чем проверено

| Утверждение | Чем |
|---|---|
| установка идемпотентна, второй прогон ничего не меняет | живой VPS, три прогона `roost up` |
| снос возвращает машину в исходное состояние | живой VPS: ни правил, ни группы, ни юнитов; чужой nginx цел |
| правила отвергают прямой выход и снимаются без следа | контейнер (`egress_container.sh`) |
| сессия с телефона запускает агента в группе | живой VPS: дерево процессов и `Groups:` |
| сертификат пускает, чужой и отозванный — нет | контейнер (`mtls_container.sh`) |
| туннель держится, ключ не даёт ни оболочки, ни второго форварда | контейнер (`tunnel_container.sh`) |
| гейт и стенд как две живые машины | **не проверялось** |
| установка PWA и импорт сертификата на телефоне | **не проверялось** |

## Разработка

```bash
make help              # список целей
make check             # линт и тесты: shellcheck, ansible-lint, bats
make test-integration  # три набора в одноразовых контейнерах (нужен docker)
```

Роли `projects` и `env_sync` прогоняются по-настоящему во временных каталогах —
нужен только ansible. Ролям нужен только `ansible.builtin`; плейбуки
запускаются из корня репозитория, там `ansible.cfg`.

## Как снести

```bash
./roost uninstall --dry-run   # показать, что уйдёт и что останется
./roost uninstall             # спросит подтверждение
./roost uninstall --purge     # плюс группа песочницы и roost.conf
```

| Уходит | Остаётся |
|---|---|
| правила и их юнит, обёртки, помощник сессий, `/etc/roost` | ваши проекты и запущенные сессии |
| терминал (его собственным установщиком), файл vhost, тулчейн сборки | бинарь агента вместе с тем, под кем он вошёл |
| туннель: юнит и ключ | сертификат — он ещё годен |
| удостоверяющий центр и каталог выдачи | всё, что roost не ставил |

Со стороны гейта снос печатает, что там осталось: удалить это может только его
владелец.

## Почему так

Обоснования решений, которые иначе выглядят произвольными.

**Почему кнопки терминала запускают агента через обёртку.** pockterm объявляет в
своём Makefile сессий `CLAUDE ?=` и `AGENT ?=`, а `?=` уступает окружению;
окружение сервиса — это его env-файл. roost владеет там двумя строками, Makefile
остаётся за pockterm, и третьей копии политики не появляется. Обратный вариант —
свой Makefile — означал бы копию, которая расходится с оригиналом при первой же
правке в pockterm.

**Почему пускателей два.** `agent-run` запускает *настроенного* агента, а всё,
что ему передали, отдаёт тому как аргументы: `agent-run qwen` запустит Claude и
вручит ему слово «qwen». Произвольные кнопки в ящике сессий передают целую
командную строку, поэтому вторая строка в env-файле (`AGENT`) указывает на
`agent-exec` — он делает первое слово командой и зовёт тот же `agent-run`.
Группа, прокси и профиль решаются по-прежнему в одном месте; без него кнопки
работали бы мимо песочницы, выглядя настроенными.

**Почему roost не становится вторым владельцем.** Ранняя версия ставила
терминал сама и на машине, где он уже был, сгенерировала ему второй токен — тот,
о котором не знал ни обратный прокси, ни ссылка из меню. Каждый запрос стал
отвечать `401`, а браузер показывал это как машину без сессий; на диагностику
ушёл вечер. Двое владельцев одного юнита ломают его при первом же расхождении.

**Почему выходной адрес — отдельная проверка.** Первый стенд, настроенный из
файла конфигурации, был направлен на локальный прокси, который отвечал, — и
выходил с адреса той же машины. `pinned` там давал предсказуемость, но не
отдельный адрес, и ни один тест такого не поймает.

**Почему сертификат едет ссылкой, а не в QR-коде.** Пакет устройства — 4.4 КБ,
в QR-код влезает 2953 байта, и код такой плотности телефон с экрана не читает.
Это замер; `tests/ca.bats` упадёт, если однажды перестанет быть правдой.

**Почему сторона гейта печатается.** У roost нет там файла состояния, он не
знает, что ещё обслуживает тот nginx, и не должен быть тем, кто его внезапно
перезагружает.

**Почему `install` не вырос в `up`.** Машины, которые уже зовут `install`, не
должны на следующем обновлении получить терминал.

Подробные записи решений — в [`docs/superpowers/specs/`](docs/superpowers/specs/).
