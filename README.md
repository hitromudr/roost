# roost

[English version](README.en.md)

Личный стенд для консольных ИИ-агентов. Машина, которая у вас есть, —
одноплатник, мини-ПК, старый ноутбук, VPS — становится сервером, где в
tmux-сессиях живут агенты (Claude Code и любые другие CLI). Их исходящий
трафик заперт в отдельной группе с предсказуемым выходом, а подключиться к
ним можно с телефона через веб-терминал.

> **Статус: в разработке.** Все части написаны — изоляция трафика,
> публикация наружу, сессии, синхронизация окружения, обёртка `roost` и
> снос. Проверены они в контейнерах и сухим прогоном; целиком, на живом
> железе от чистой машины до телефона, стенд ещё не собирали.

## Быстрый старт

```bash
git clone https://github.com/<owner>/roost && cd roost
./roost setup      # несколько вопросов, ответы уходят в roost.conf
./roost install    # применить к этой машине
./roost doctor     # проверить, что стенд — то, чем себя называет
```

Если стенд за NAT, понадобится машина с публичным адресом:

```bash
./roost gate add user@vps.example   # nginx, TLS, клиентские сертификаты
./roost qr                          # QR со ссылкой для телефона
```

## Что делают роли

| Роль | Где | Что |
|---|---|---|
| `egress_sandbox` | стенд | группа и правила `gid-owner`, обёртка запуска агента |
| `agent_sessions` | стенд | tmux-сессии по проектам, mouse mode для телефона |
| `publish` | стенд | веб-терминал через его же установщик, обратный тоннель |
| `gate` | публичный вход | nginx с TLS, клиентский CA, аккаунт для тоннеля |

Плейбуки запускаются из корня репозитория — там `ansible.cfg`, который
указывает на `ansible/roles`. Перед первым запуском `make deps`.

## Зачем

Разработка с агентом привязывает вас к машине, на которой он запущен.
Ноутбук закрыт — работа стоит. Перенести агента на постоянно включённый
сервер несложно, но всплывают три вещи, которые приходится решать каждому
заново:

- **Выход в интернет.** Агенту нужен доступ к своему API. Если сервер меняет
  сеть или стоит за NAT, внешний адрес плавает. roost запирает трафик агента
  в группе, которой разрешён только локальный прокси, — выход становится
  предсказуемым и не зависит от того, где сейчас находится машина.
- **Доступ снаружи.** Сервер дома не имеет публичного адреса. roost поднимает
  обратный тоннель на любую машину с публичным адресом и ставит перед ним
  TLS с аутентификацией.
- **Окружение.** Агент полезен настолько, насколько ему знакома ваша среда:
  конфиги, ключи, контекст проектов. roost переносит их между рабочей машиной
  и стендом, храня секреты зашифрованными.

## Архитектура

| Узел | Что это | Обязателен |
|---|---|---|
| `stand` | машина, где работают агенты, обычно за NAT | да |
| `gate` | публичная точка входа | нет, если стенд публичный |
| `workstation` | машина, с которой вы работаете | да |

Телефон подключается к `gate` по TLS, тот через тоннель отдаёт веб-терминал
на `stand`, за терминалом — tmux с агентом. Сам агент ходит наружу только
через локальный прокси: прямой выход его группе запрещён правилами
файрвола.

## Модель безопасности

Прочитайте до установки: **веб-терминал отдаёт полную оболочку тому, кто до
него дошёл.** Относитесь к стенду как к SSH-доступу. Публикация наружу без
TLS и аутентификации недопустима, и установщик на это не согласится.

Изоляция агента здесь — про предсказуемость исходящего трафика, а не про
защиту от вредоносного кода: агент работает от вашего пользователя и делает
с вашими файлами то же, что и вы.

## Как снести

```bash
./roost uninstall --dry-run   # показать, что уйдёт и что останется
./roost uninstall             # спросит подтверждение
./roost uninstall --purge     # плюс группа, токен и roost.conf
./roost gate remove user@vps.example
```

Уходят: правила и их юнит, обёртка запуска, помощник сессий, тоннель,
веб-терминал с его юнитом и клоном, каталог `/etc/roost`. Остаются ваши
проекты и запущенные сессии — их снос требует явного решения, а не флага по
умолчанию. С `--purge` дополнительно удаляются группа песочницы,
`/etc/pockterm` с токеном и сам `roost.conf`.

На публичном входе `gate remove` убирает vhost и учётную запись тоннеля, но
оставляет клиентский CA: его удаление обесценивает сертификаты, уже
установленные на устройствах. `--purge` снимает и его. TLS-сертификат
домена не трогается ни в каком случае.

Проверено в контейнере: после сноса не остаётся ни одного правила ни в
IPv4, ни в IPv6, и машина возвращается в исходное состояние.
