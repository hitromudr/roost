# roost

[English version](README.en.md)

Место, где консольный ИИ-агент работает под присмотром. Машина, которая у вас
есть, — одноплатник, мини-ПК, старый ноутбук, VPS — получает группу с
предсказуемым выходом в интернет, обёртку запуска агента, tmux-сессии по
проектам, одинаковую с остальными машинами раскладку репозиториев и окружения
— и веб-терминал, чтобы дойти до всего этого с телефона.

> **Статус: в разработке.** Изоляция трафика, сессии, синхронизация
> окружения, раскладка проектов, обёртка `roost` и снос — написаны и
> проверены на живом железе (Raspberry Pi): установка идемпотентна на втором
> прогоне, группа и правила появляются, снос не оставляет ни файлов, ни
> правил ни в одной адресной семье. Установка агента, терминала и внешнего
> входа — с 2026-08-05.

## Быстрый старт

```bash
git clone https://github.com/hitromudr/roost && cd roost
./roost up
```

Одна команда, потому что каждый её шаг всё равно пришлось бы сделать: спросить
несколько вещей и записать ответы в `roost.conf`, поставить ansible, если его
нет, поставить агента, если его нет, завести группу и правила, поднять
веб-терминал на loopback, выпустить сертификат, добавить свой vhost — и
напечатать QR-код. Наводите камеру, выбираете «добавить на главный экран», и
терминал ведёт себя как приложение.

Шаги существуют и по отдельности, потому что каждый касается того, у чего на
машине может быть свой владелец:

```bash
./roost setup      # вопросы; ответы уходят в roost.conf
./roost agent      # поставить агента, если его тут нет
./roost install    # песочница, сессии, окружение
./roost terminal   # веб-терминал — только там, где его нет
./roost expose     # TLS впереди него, и адрес, который он получил
./roost qr         # QR-код для телефона
./roost doctor     # проверить, что песочница — то, чем себя называет
```

`install` намеренно означает ровно то, что означал раньше: песочница, сессии,
окружение. Машины, которые уже зовут его, не должны на следующем обновлении
получить веб-терминал.

Профили `pinned` и `proxied` требуют `PROXY_URL` в
`/etc/roost/agent-proxy.env` (0640, владелец — учётная запись агента). Без
него агент остаётся **без сети вообще**, и `doctor` говорит об этом прямо.
`roost setup` спрашивает прокси сразу — так этот файл не остаётся домашним
заданием. Все ответы можно и просто написать руками: `roost.conf.example`
рядом, с объяснением каждой строки.

> **Проверьте выходной адрес прежде, чем входить агентом в аккаунт.** Прокси,
> который отвечает, — это ещё не прокси, который меняет адрес: локальный
> `3proxy` на том же сервере выпустит трафик с адреса этого же сервера. Для
> провайдера запрос с неожиданного адреса — повод приостановить учётную
> запись, и это стоит дороже вечера отладки. `roost doctor` печатает реальный
> адрес и сверяет его с `expected_exit` из `roost.conf`; пока там пусто, он
> говорит, что сравнивать было не с чем.

## С телефона

`roost expose` ставит TLS перед терминалом на этой же машине: свой файл vhost
в nginx, сертификат Let's Encrypt и порт, который никем не занят (`8443` по
умолчанию — `443` на живых машинах почти всегда чей-то). Домена может не быть
вовсе: тогда имя выводится из адреса машины через `sslip.io`
(`203-0-113-5.sslip.io`), и сертификат всё равно настоящий — а значит,
страницу можно поставить как приложение.

Дальше `roost qr` печатает код: адрес вместе с токеном. Токен лежит в ссылке,
которую сохранит телефон, — то есть и в истории браузера, и в логах того, что
стоит впереди. Для постоянной установки есть второй замок — ниже.

### Машина без адреса: гейт

Одноплатник дома, ноутбук в офисе, мини-ПК за NAT — у них нет адреса, на который
телефон мог бы прийти. Тогда нужна вторая машина с маршрутизируемым адресом,
и `gate=` в `roost.conf` говорит, какая:

```
gate=roost-tunnel@vps.example
```

`./roost tunnel` поднимает на стенде **свой** ключ и юнит, который держит один
обратный форвард к гейту. `./roost gate` печатает то, что нужно добавить **там**:

- строку в `authorized_keys`, разрешающую ровно один форвард и больше ничего
  (`restrict,port-forwarding,permitlisten="127.0.0.1:18130"` — ни оболочки, ни
  агента, ни второго порта);
- файл `/etc/ssh/sshd_config.d/roost-tunnel.conf`, без которого укреплённый sshd
  форвард просто не разрешит — и на стенде это выглядит как туннель, который не
  держится, а на гейте не выглядит никак;
- файл `/etc/nginx/conf.d/roost-terminal.conf`, который отдаёт терминал через
  этот форвард, и команду certbot для сертификата: адрес у гейта, значит и имя
  доказывает он.

Печатается, а не применяется, потому что гейт — чужая машина: у roost там нет
файла состояния, он не знает, что ещё обслуживает тот nginx, и не должен быть
тем, кто его внезапно перезагружает. `./roost gate --apply` сделает это по вашему
ssh-доступу, если попросить: три файла с именем roost и одна строка, аккаунт
создаёт владелец сам.

Проверяется контейнером (`make test-integration`): форвард держится, гейт достаёт
терминал на стенде, а тем же ключом нельзя ни получить оболочку, ни открыть
второй форвард.

### Второй замок: сертификат на устройстве

`client_auth=mtls` в `roost.conf` — и дверь спрашивает клиентский сертификат
вместо токена. roost держит свой удостоверяющий центр и выдаёт по одному
устройству:

```bash
./roost enroll phone
```

Печатается QR с **одноразовой ссылкой** на пакет устройства и пароль, который
спросит импортёр. Сам сертификат в QR не поедет, и это замер, а не мнение:
пакет — 4.4 КБ, в код влезает 2953 байта, а код такой плотности телефон с
экрана не читает. Поэтому в коде ссылка, ссылка живёт десять минут — использовали
её или нет, — и за ней лежит файл, который без пароля не импортируется.

Потерянный телефон убирается из доступа:

```bash
sudo roost-ca revoke phone && sudo systemctl reload nginx
```

Отзыв работает через список отзыва, который читает nginx: тот же сертификат,
который минуту назад пускал, перестаёт пускать, а остальные устройства не
задеты. Это проверяется контейнерным тестом (`make test-integration`), а не
обещается: без сертификата — отказ, с сертификатом — вход, чужой сертификат —
отказ, путь выдачи открыт тому, у кого сертификата ещё нет, каталог выдачи не
листается.

Кнопки в ящике сессий запускают агента **через песочницу**: pockterm объявляет
в своём Makefile `CLAUDE ?=` и `AGENT ?=`, `?=` уступает окружению, а окружение
сервиса — это его env-файл. Поэтому Makefile остаётся за pockterm, политика — за
roost, и третьей копии ни того, ни другого не появляется. `doctor` проверяет
именно это: кнопки, которые работают, но ничего не изолируют, выглядят как
успех.

### Второй агент — ещё одно имя, а не вторая обёртка

Строка `agents=` в `roost.conf` перечисляет остальных агентов, `имя:команда`
через запятую:

```
agents=codex:/home/you/.local/bin/codex
```

`roost install` ставит `/usr/local/bin/codex-safe` — ссылку на тот же
`agent-run` — и `/etc/roost/agents/codex.env`, где назван только бинарь.
Группа, прокси и профиль остаются машинными: политика на всех агентов одна, а
не по копии на каждого. Обёртка на агента означала бы копию политики на
агента, а копии расходятся.

## Что делают роли

| Роль | Что |
|---|---|
| `egress_sandbox` | группа и правила `gid-owner`, обёртки запуска агента |
| `agent_cli` | сам бинарь агента, если его на машине нет |
| `agent_sessions` | tmux-сессии по проектам, mouse mode для телефона |
| `projects` | клоны репозиториев из `projects.conf` |
| `env_sync` | репозиторий окружения и его установщик |
| `terminal` | веб-терминал на loopback — там, где своего нет |
| `expose` | TLS впереди него: свой vhost и свой сертификат |

Ролям нужен только `ansible.builtin` — никаких коллекций ставить не надо.

### Проекты: список, а не раздача

`projects.conf` перечисляет репозитории, которые должны быть на **каждой**
машине, откуда вы работаете:

```
isearch  https://git.example/isearch.git
sorter   https://github.com/x/sorter.git  develop
```

`./roost projects` приводит ту машину, где запущен, к этому списку. Общее
состояние держит репозиторий, а не одна из машин, поэтому команда одинаково
уместна и там, где живут агенты, и на рабочем ноутбуке.

Ничего существующего при этом не переписывается. Клон с незакоммиченной
работой называется и пропускается; имя, занятое каталогом без `.git`
(развёрнутый артефакт, цель деплоя), — тоже, и остальной список всё равно
раскладывается. Ветку можно не указывать — тогда берётся ветка репозитория
по умолчанию.

Окружение (`env_sync`) устроено так же: репозиторий с конфигами
выкладывается и запускается его собственный установщик. Если в нём есть
зашифрованные файлы (`*.sops.*`), роль требует age-ключ на месте — без него
секреты молча останутся зашифрованными, а установщик отчитается об успехе.

Плейбуки запускаются из корня репозитория — там `ansible.cfg`, который
указывает на `ansible/roles`.

## Зачем

Разработка с агентом привязывает вас к машине, на которой он запущен.
Ноутбук закрыт — работа стоит. Перенести агента на постоянно включённый
сервер несложно, но всплывают две вещи, которые приходится решать каждому
заново:

- **Выход в интернет.** Агенту нужен доступ к своему API. Если сервер меняет
  сеть или стоит за NAT, внешний адрес плавает. roost запирает трафик агента
  в группе, которой разрешён только локальный прокси, — выход становится
  предсказуемым и не зависит от того, где сейчас находится машина.
- **Окружение.** Агент полезен настолько, насколько ему знакома ваша среда:
  конфиги, ключи, контекст проектов. roost раскладывает их одинаково на всех
  машинах, а секреты держит зашифрованными.

Третья вещь — дойти до машины с телефона — решается тем же одним прогоном, но
по правилам, описанным ниже: не вместо того, что на машине уже есть, а рядом.

## Границы

Машина, где стоит агент, обычно не пустая: на ней уже есть веб-терминал,
тоннели, чужие юниты и своя история. Правило здесь одно: **roost владеет
только тем, что сам поставил.**

Это не осторожность ради красоты. Ранняя версия ставила веб-терминал сама и
на машине, где он уже был, сгенерировала ему второй токен — тот, о котором не
знал ни обратный прокси, ни ссылка из меню. Каждый запрос стал отвечать
`401`, а браузер показывал это как машину без сессий; на диагностику ушёл
вечер. Двое владельцев одного юнита ломают его при первом же расхождении, и
единственная надёжная защита — не становиться вторым.

Поэтому внешний вход, вернувшийся в проект в 2026-08, устроен так:

- **Терминал ставится только там, где своего нет.** `pockterm.service` без
  `/etc/roost/terminal.env` рядом — признак чужого владельца, и роль
  останавливается, объясняя, что делать вместо этого.
- **roost владеет файлами, а не сервисами.** В чужой nginx добавляется один
  файл, `nginx -t` проверяется до перезагрузки, и при отказе файл забирается
  назад: битый файл в `conf.d` ломает не только терминал, но и все
  перезагрузки соседних vhost. Сама перезагрузка — с явного согласия, `roost
  expose` про это спрашивает.
- **Чего roost не может присвоить, он печатает.** Если входную дверь держит
  то, куда файл не положить (например, Caddy, настроенный через admin API), —
  печатается маршрут, который нужно добавить, и на этом всё.
- **Всё добавленное снимается по имени.** Снос читает файлы состояния и
  удаляет перечисленное там; pockterm при этом сносится **его собственным**
  установщиком — владелец своих файлов остаётся один до самого конца.

## Модель безопасности

Изоляция агента здесь — про предсказуемость исходящего трафика, а не про
защиту от вредоносного кода: агент работает от вашего пользователя и делает
с вашими файлами то же, что и вы.

**Терминал отдаёт полную оболочку тому, кто до него дошёл.** Относитесь к
такому адресу как к SSH — и когда сессии отдаёте наружу чем-то своим, и когда
это делает `roost expose`. По умолчанию дверь закрыта токеном за TLS: этого
хватает, чтобы начать, и это то, что делает первый запуск одной командой. Токен
живёт в ссылке — значит, и в истории браузера, и в логах фронта. Для постоянной
установки ставьте впереди клиентские сертификаты.

## Разработка

```bash
make help     # список целей
make check    # линт и тесты
```

Роли `projects` и `env_sync` покрыты тестами, которые прогоняют их
по-настоящему во временных каталогах — нужен только ansible, ни docker, ни
root. Там, где ansible нет, эти тесты пропускаются.

`make test-integration` проверяет саму политику в одноразовом контейнере:
прямой выход для группы отвергается, локальный прокси остаётся доступен,
процессы вне группы не затронуты, повторное применение ничего не меняет, а
после `clear` не остаётся правил ни в одной адресной семье. Нужен docker.

Чего не проверит ни один тест — с какого адреса агент выходит в интернет.
Это спрашивает `roost doctor`, и на машине с чужим прокси смотреть надо
сначала туда: неожиданный адрес стоит учётной записи, а не вечера отладки.

## Как снести

```bash
./roost uninstall --dry-run   # показать, что уйдёт и что останется
./roost uninstall             # спросит подтверждение
./roost uninstall --purge     # плюс группа песочницы и roost.conf
```

Уходят: правила и их юнит, обёртки запуска, помощник сессий, каталог
`/etc/roost`, а если их ставил roost — веб-терминал (его собственным
установщиком), файл vhost и скачанный для сборки тулчейн. Остаются ваши проекты
и запущенные сессии — их снос требует явного решения, а не флага по умолчанию,
— бинарь агента вместе с тем, под кем он вошёл, сертификат (он ещё годен) и
всё, что roost не ставил.

Проверено в контейнере: после сноса не остаётся ни одного правила ни в
IPv4, ни в IPv6, и машина возвращается в исходное состояние.
